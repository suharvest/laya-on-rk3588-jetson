# RK3588（Rockchip NPU）路径

本篇讲 RK3588 上的移植：RKNPU 的 surface 上限如何决定 `seq` 桶、掩码子图的两处图手术，以及交付配置与实测数字。

## 背景约束

`laya` 是非自回归双向编码器：一次前向对序列上各 marker 位置并行打分。RKNN 要求固定 shape，
所以 seq（状态文本 + 问题 + 选项标签的总 token 数）必须预先选定为一个"桶"。

**RK3588 上 seq 的上界是 90**，来自 RKNPU 的一条限制：attention 分数矩阵的 surface 为 `seq × seq`，
而算子转置的 `H × W` 乘积上限是 8192。

```text
W RKNN: Transpose will fallback to CPU, because input shape has exceeded the max limit,
        height(512) * width(512) = 262144, required product no larger than 8192!
```

超出即静默回退到 CPU（`W` 级警告，不中断构建）。实测代价：

| seq | 延迟 | attention 落点 |
|---|---|---|
| 64 | 149.2 ms | NPU |
| 90 | 280.6 ms | NPU |
| 512 | 8840 ms | CPU 回退 |

Jetson 无此限制（TensorRT 无 surface 上限，也无 RKNN 那种 CPU 回退算子缺口），见 [jetson.md](jetson.md)。

## 交付配置

**seq=512**（用户选定）。桶形状固定，短输入亦按 512 计费。

| 平台 | 产物 | p50 | 精度 |

| RK3588（Radxa ROCK 5T） | `oldship.s512.m16.fp16.nanguard.sharedmask.rk3588.rknn` | **509 ms** | top1 16/16 |
| Jetson Orin NX / Nano | `laya.s512.fp16.engine` | **18.9 / 22.0 ms** | top1 16/16 |

## 精度问题：真因是掩码构造的跨载体依赖

融合（`exSDPAttention`）曾被认为导致精度崩（top1 5/16）。**该结论被推翻**——用官方开关
`disable_rules=['fuse_matmul_softmax_matmul_to_sdpa']` 关掉融合后，精度**没有回来**（4/16）。

三轮单变量切分点名了真正的致错元素：

| 轮 | 改动 | 设备 top1 | 判定 |
|---|---|---|---|
| base | 未改 | 16/16 | 正确 |
| R1 | 去掉 `Not` | 7/16 | FAIL |
| R2 | `Mul` 乘数 `+3.4028e38` → `+65504` | 10/16 | FAIL，**与原件七位有效数字全同** |
| **R3** | **去掉嵌套 `Where`** | **16/16** | **PASS，逐位同基线** |

**致错的是「某份掩码的 `Where` 以另一份掩码为载体分支」这种跨载体依赖**（另一条导出链路的
`/encoder/Where_2` 形态）。`Not` 不是必需元素；数值范围不是病因（R2 把乘数换成 fp16 可表示的
值后设备输出**逐位不变**）。

> **规则：掩码载体必须彼此独立。**
> `Where(cond, 0.0, −inf)` 或 `Mul(Sub(Cast(cond),1), +FLT_MAX)` 各自独立都正确；
> 不要让一份掩码由另一份派生。

## 性能问题：掩码的每层重复物化

正确的那条导出链路在 **22 个 attention 层里各自物化了一份 `[1,1,S,S]` 掩码**；另一条链路把它
提到 encoder 层算一次。前者净多搬 **147.7 MB / 次推理**（S=512），对应 **+160.5 ms**——
隐含有效带宽 899 MB/s（同一算法在 S=90 预测 4.96 ms、实测 +6.92 ms 佐证）。

把 per-layer 掩码改成共享后：

| 桶 | ORT 逐位比对 | 判定 |
|---|---|---|
| **s90** | `logits_maxabs = 0.0`、`act_maxabs = 0.0`、掩码 352/352 | **真的逐位一致** |
| **s512** | `logits_maxabs = nan`、`act_maxabs = nan` | **该次比对无效**（见下） |

- 延迟：**s512 807 → 597.68 ms**
- s512 交付物的正确性**不**由上面那次 ORT 比对支撑，而由**设备级验收**支撑：对 nanfix
  参照 top1 16/16、order_exact 15/16（`lockfreq/s512.lock.rank.json`）

> ⚠️ **s512 的 ORT 比对为何无效**：`S4_ort_bitexact.py` 用 `np.asarray(x).tobytes() == ...`
> 比较，而 s512 的 nanguard 图在 ORT fp32 下于 live 位置**全部输出 NaN**——NaN 位模式相同，
> 字节比较恒真，于是报告 "BIT_EXACT"。s90 同一手术下无 NaN，所以那次是有效比较。
> 两条原始记录：`structprobe/s4_bitexact_s{90,512}.log`。

> ⚠️ **未解释**：为什么 s512 的 nanguard 图在 ORT fp32 下 NaN、而同一手术在 s90 上不 NaN，
> 以及它转成 RKNN 后在设备上为何又能正常工作。**需核实。**

> **规则：掩码不要每层重复物化。**
>
> **规则：逐位比较前先确认没有 NaN。** 字节级比较对 NaN 恒真，会把"两边都是 NaN"报成"完全一致"。

## 精度与性能同源于掩码子图，却是两个独立维度

| 维度 | 影响 |
|---|---|
| **依赖关系**（载体是否交叉） | → **正确性** |
| **冗余度**（是否每层重复） | → **速度** |

把二者当成一个根因会导致连续的错误方向。本次排查早期即如此。
