# 测量纪律

本篇讲本次评测里影响数字可信度的测量坑：哪些协议变量会把 p50 抬高数倍，以及报数时应取哪个统计量。

## 测量纪律（本次踩过的坑，影响数字可信度）

1. **CPU 亲和性可造成 3× 误差**：`rknnlite.inference()` 含 host 侧张量拷贝，跑在 CPU 上且与 NPU 串行。
   钉到 `little`（cpu0-3，A55）把 p50 从 ~80 ms 抬到 ~264 ms。**测量一律 unpinned。**
2. **NPU 频点不是漂移来源**：`/sys/class/devfreq/fdab0000.npu/trans_stat` 显示
   `Total transition : 0`——自开机起全程 1.0 GHz。
3. **锁频后 s512 的 p50 才收成单值**（轮间比 1.033）；s90 未收成，残余来源是 **CPU 簇落点**
   （A76 74.82 ms / A55 104.21 ms，簇内 iqr 仅 0.36/0.39 ms）。
4. **报 min 或锁频后 p50**，不要报未锁频的单点 p50。
5. **参考文件必须配对**：用 s90 的 ORT 参考评 s512 输出会得 13/16 FAIL，那是参考错配。
   反过来，交付物与它实际配对的参照也要查证过——本项目的 RK3588 交付物配的是
   **nanfix** 参照，不是同目录下那张 nanguard 参照（后者在 live 位置全是 NaN，无法排序）。
6. **逐位比较前先确认没有 NaN**。本项目的 s512 ORT 比对用了 `tobytes()` 相等，
   而两侧在 live 位置都是 NaN——位模式相同，比较恒真，报出 "BIT_EXACT"。
   **s90 那次是真的（`maxabs = 0.0`），s512 那次什么都没测。**
   字节比较、`==`、`max()` 遇到 NaN 都会给出误导性结果；比对前先 `np.isnan(...).any()`。
