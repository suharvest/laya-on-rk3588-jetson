# laya 在 Rockchip NPU 与 Jetson 上的部署评测

对 TypeSafe Jev 的开源替代 [`laya`](https://github.com/NandhaKishorM/laya)（`convaiinnovations/laya-multilingual`，
mmBERT-base 322M 双向编码器决策模型）在三类边缘设备上的移植、精度与性能评测。

**交付配置：seq=512。**

| 平台 | 产物 | p50 | 精度 |
|---|---|---|---|
| RK3588（Radxa ROCK 5T） | `oldship.s512.m16.fp16.nanguard.sharedmask.rk3588.rknn` | **509 ms** | top1 16/16 |
| Jetson Orin NX / Nano | `laya.s512.fp16.engine` | **18.9 / 22.0 ms** | top1 16/16 |

产物路径与校验值见 [ARTIFACTS.md](ARTIFACTS.md)，脚本见 [`scripts/`](scripts/)，
关键原始输出见 [`evidence/`](evidence/)。

---

## 1. 背景约束

`laya` 是非自回归双向编码器：一次前向对序列上各 marker 位置并行打分。RKNN 要求固定 shape，
所以 seq（状态文本 + 问题 + 选项标签的总 token 数）必须预先选定为一个"桶"。

**RK3588 上 seq 的上界是 90**，来自 RKNPU 的一条限制：attention 分数矩阵的 surface 为 `seq × seq`，
而算子转置的 `H × W` 乘积上限是 8192。

```
W RKNN: Transpose will fallback to CPU, because input shape has exceeded the max limit,
        height(512) * width(512) = 262144, required product no larger than 8192!
```

超出即静默回退到 CPU（`W` 级警告，不中断构建）。实测代价：

| seq | 延迟 | attention 落点 |
|---|---|---|
| 64 | 149.2 ms | NPU |
| 90 | 280.6 ms | NPU |
| 512 | 8840 ms | CPU 回退 |

Jetson 无此限制（TensorRT 无 surface 上限，也无 RKNN 那种 CPU 回退算子缺口）。

## 3. 关键结论

### 3.1 精度问题：真因是掩码构造的跨载体依赖

融合（`exSDPAttention`）曾被认为导致精度崩（top1 5/16）。**该结论被推翻**——用官方开关
`disable_rules=['fuse_matmul_softmax_matmul_to_sdpa']` 关掉融合后，精度**没有回来**（4/16）。

三轮单变量切分点名了真正的致错元素：

| 轮 | 改动 | 设备 top1 | 判定 |
|---|---|---|---|
| base | 未改 | 16/16 | 正确 |
| R1 | 去掉 `Not` | 7/16 | FAIL |
| R2 | `Mul` 乘数 `+3.4028e38` → `+65504` | 10/16 | FAIL，**与原件七位有效数字全同** |
| **R3** | **去掉嵌套 `Where`** | **16/16** | **PASS，逐位同基线** |

**致错的是「某份掩码的 `Where` 以另一份掩码为载体分支」这种跨载体依赖**（另一条导出链路的
`/encoder/Where_2` 形态）。`Not` 不是必需元素；数值范围不是病因（R2 把乘数换成 fp16 可表示的
值后设备输出**逐位不变**）。

> **规则：掩码载体必须彼此独立。**
> `Where(cond, 0.0, −inf)` 或 `Mul(Sub(Cast(cond),1), +FLT_MAX)` 各自独立都正确；
> 不要让一份掩码由另一份派生。

### 3.2 性能问题：掩码的每层重复物化

正确的那条导出链路在 **22 个 attention 层里各自物化了一份 `[1,1,S,S]` 掩码**；另一条链路把它
提到 encoder 层算一次。前者净多搬 **147.7 MB / 次推理**（S=512），对应 **+160.5 ms**——
隐含有效带宽 899 MB/s（同一算法在 S=90 预测 4.96 ms、实测 +6.92 ms 佐证）。

把 per-layer 掩码改成共享后：

- ORT 逐位等价：logits 16/16、act_logits 16/16、**掩码张量 352/352 BIT_EXACT**
- 设备输出与基线 **`rel_l2 = 0.000000`（逐位相同）**
- **s512 807 → 597.68 ms**

> **规则：掩码不要每层重复物化。**

### 3.3 精度与性能同源于掩码子图，却是两个独立维度

| 维度 | 影响 |
|---|---|
| **依赖关系**（载体是否交叉） | → **正确性** |
| **冗余度**（是否每层重复） | → **速度** |

把二者当成一个根因会导致连续的错误方向。本次排查早期即如此。

### 3.4 量化：三平台六次尝试、三套机制，天花板在量化口径

| 尝试 | 结果 | 机制 |
|---|---|---|
| RKNN int8 | top1 3/16 | 输出 logits 塌缩成分段常数 |
| RKNN w4a16 | top1 6/16 | `rel_l2_full=7.1e-05` 看着比 fp16 还好，排序破损 |
| RKNN w8a16 | 不支持 | 两平台 config 直接拒绝 |
| Jetson INT4 WoQ | **慢 1.62×**，top1 10/16 | **sm_87 无融合 int4 kernel**，走"反量化成 fp16 再 GEMM"（流量 1.18+4.72+4.72 MB；融合只需 2.3 MB） |
| Jetson INT8 隐式 PTQ | **0/229 个 int8 层**，与 fp16 逐位相同 | **构建器未生成 int8 候选**：117 个 `ONNXTRT_Broadcast_*` 中间量缺 scale 导致级联回退 |
| **Jetson INT8 显式 Q/DQ** | **快 1.28–1.31×，top1 5–6/16** | int8 真启用，但 per-tensor 激活 scale 削顶 |

#### 3.4.1 显式 Q/DQ：唯一真正落到 int8 核的路径

| 指标 | fp16 | 显式 Q/DQ |
|---|---|---|
| int8 层 | 0 / 229 | **247 / 259（95.4%）** |
| GEMM kernel | fp16 | 101 个全走 `sm80_xmma_..._i8i8_i8i32_..._tensor16x8x32` |
| 权重内存 | 644,347,908 B | **523,255,044 B**（−18.8%） |
| engine | 650,779,868 B | 525,664,180 B（−19.2%） |
| fallback 日志 | 60+ 条 `Missing scale and zero-point` | **0 条** |

延迟（runner p50，nx）：**17.416 → 13.359 ms（1.315×）**；nano 1.35×。oracle 预估上限是 9–13%
（只算权重流读 + tensor core），实测超出。

> 隐式 PTQ 那个 `laya.s512.int8.engine` 经复核与 fp16 engine **逐位相同**
> （`bitwise_equal 16/16, max_absdiff 0.0`，两者同为 620.63 MB）——builder 全程选了 fp16 kernel，
> 隐式 int8 这条路径实际**从未跑起来过**。

#### 3.4.2 精度不可用，病因定位到第一次量化

| 轮 | 改动 | 排序 |
|---|---|---|
| fp16 基线 | — | **16/16** 逐位一致 |
| qdq1 | 全 GEMM 输入+输出插 Q/DQ | 6/16 |
| qdq2 | 48 个残差 GEMM 去掉输出侧 Q/DQ（skip 留 fp16） | **5/16**（残差流假设**证伪**） |

qdq2 里残差确实回到了 fp16（`__myl_FcCasAdd_myl0_*` 的首输入与输出都是 `Half [1,512,768]`），
gemm 也没掉出 int8（48 个变成带残差 Add 的 int8 融合核），**唯一变量改对了，精度没回来**。

而且病征在两轮里**一字未动**——`-4.640625` 出现在完全相同的 rows（5/7/8/12/14），数值精确相同。
病因在两者都没碰过的地方。

用 ORT 逐张量比对定位（Q/DQ 在 ORT 里是真实算子，饱和算术与 TRT 相同），
**第一个发散张量在 encoder 的第一次量化激活上**：

```
/encoder/embeddings/norm/LayerNormalization_output_0
  ref  min/max : -13.3452 / +27.8868
  qdq  min/max :  -4.00049 /  +3.96924     (= -128·s / +127·s)
  scale = 0.0312538     127·s = 3.969     饱和比 max|ref|/(127·s) = 7.03
```

第一次量化就把 27.9 的激活钳到 3.97。全量 **148 个激活站点**：

| 口径 | row 0 | row 14 |
|---|---|---|
| rel > 0.05 | **148 / 148** | **148 / 148** |
| 饱和比 > 1（真在削顶） | 118 / 148 | 135 / 148 |
| rel_l2 中位数 | 0.744 | 0.722 |

> `-4.640625` 那个地板的机制已证实：它是 `/scorer/scorer.3/MatMul_output_0` 的
> `-128·s = -4.66036` 经一次 bias Add 得到的（差 0.0198 即该位置 bias）。
> 但它是**结果不是原因**——走到那一层时上游早已面目全非，同一站点 fp32 的 max 是 +16.61，
> qdq 只剩 +0.40。

**天花板定位**：这颗芯片有 int8 tensor core（sm_87），这套工具链能让 95.4% 的层落到 int8，
限制不在硬件也不在工具链，而在 **per-tensor 激活量化的口径本身**——322M 双向编码器里存在
承载信号的离群通道，per-tensor 的对称 int8 域装不下它。

> 若还要再走，方向是换量化口径（per-channel 激活 / SmoothQuant 一类离群通道抑制），
> **不是**再动 Q/DQ 的插入位置——两轮单变量已经证明插入位置不是病因。

### 3.5 8k 上下文：不可用，且主因在模型

用"植入事实"构造有标准答案的样本（4 选 1，chance 25%）：

| seq | **ORT fp32（不含 fp16 误差）** | TRT fp16 | 延迟（nx / nano） |
|---|---|---|---|
| 512 | **52.5%**（+4.0σ，显著） | 52.5% | 18.9 / 22.0 ms |
| 2048 | 30.0% | 30.0% | 119.7 / 141.5 ms |
| **8192** | **36.0%**（+1.8σ，**与 chance 不可区分**） | 28.0% | 1303.8 / 1417.2 ms |

**不存在"随长度衰减的曲线"，而是 512 可用、2048 之后直接掉到 chance 附近。**
2048/8192 的失败**主要是模型本身**（fp32 参考自己就只有 30–36%），部署保真度（fp16 vs fp32）
是叠加的、次要的因素。

**位置效应明确**（长上下文的经典失效模式）：8192 上植入点贴 marker 时 8/10，最远端 **0/10**。

**多语言**：512 上五个语种（en/zh/es/ja/ar）表现一致（各 4–5/8），脚本差异不产生可测差异；
8192 上没有可用语种。

> 注：该探针是"从 ~8000 token 取回一个数、并在 3 个诱饵中绑定对类别"，比 laya 自身判定
> benchmark 更硬。laya README 记载的"~4000 token 内 20 条对 16–18 条"测的不是同一件事，
> 两边结论不冲突。

### 3.6 Jetson 的瓶颈构成（s512，18.5 ms）

| 项 | ms | 占比 |
|---|---|---|
| FFN 升维/门控 FC | 4.592 | 24.8% |
| attention（`_gemm_mha_v2`） | 4.074 | 22.0% |
| QKV 投影 | 3.061 | 16.5% |
| FFN 降维 | 2.080 | 11.2% |
| norm / residual 逐元素 | 1.704 | 9.2% |
| attn 输出投影 | 1.324 | 7.1% |
| rotary | 1.228 | 6.6% |

- **229 个 kernel 严格串行**：节点耗时之和 / 端到端 = **1.001**（graph）、0.987（non-graph），无并行余量
- **瓶颈是「串行链 + 带宽」的混合**：nano(6 SM)/nx(8 SM) 每节点耗时比——norm/residual **1.049**、
  rotary **1.033**（与 SM 数无关 ⇒ 带宽受限）；GEMM/attention 1.12–1.16（部分算力受限）。
  少 25% SM 只慢 12–16%（纯算力受限应为 33%）
- **s90 → s512 标度**：attention **×8.95**（O(n²)），所有线性层仅 **×1.94–2.40**。
  线性层在 s90 是延迟受限，s512 上每 token 效率反而提升 2.9×
- 三点拟合：`T(n) ≈ 3.26 + 0.0182·n + 1.85e-5·n²` ms（s512：固定 18.7% + 线性 53.4% + 二次 27.9%）
- **decoder head 仅 2 层却占 9.2%**，其 4 个大 GEMM 在 M=16 下只跑到 0.41–0.42 TFLOP/s（约 fp16 峰值的 2%）

### 3.7 CUDA Graph：可用但收益随 seq 衰减

| 配置 | non-graph → graph | 节省 | 加速比 |
|---|---|---|---|
| nx s90 | 6.543 → 5.076 ms | 1.467 ms | 1.289× |
| nx s512 | 18.994 → 17.563 ms | 1.431 ms | **1.081×** |
| nx s2048 | 119.314 → 118.107 ms | 1.207 ms | 1.010× |
| nano s512 | 21.451 → 20.406 ms | 1.045 ms | 1.051× |

**精度零损失**：graph vs non-graph **16/16 逐位相同**，`max_abs_diff` **精确为 0.0**。

**节省是与 seq 无关的常数 ~1.0–1.6 ms**（消除的是主机侧 enqueue 间隙），
所以它是"顺手开启项"而非 s512 的杠杆。s90 档（1.29×）才是它真正赚钱的地方。

## 4. 测量纪律（本次踩过的坑，影响数字可信度）

1. **CPU 亲和性可造成 3× 误差**：`rknnlite.inference()` 含 host 侧张量拷贝，跑在 CPU 上且与 NPU 串行。
   钉到 `little`（cpu0-3，A55）把 p50 从 ~80 ms 抬到 ~264 ms。**测量一律 unpinned。**
2. **NPU 频点不是漂移来源**：`/sys/class/devfreq/fdab0000.npu/trans_stat` 显示
   `Total transition : 0`——自开机起全程 1.0 GHz。
3. **锁频后 s512 的 p50 才收成单值**（轮间比 1.033）；s90 未收成，残余来源是 **CPU 簇落点**
   （A76 74.82 ms / A55 104.21 ms，簇内 iqr 仅 0.36/0.39 ms）。
4. **报 min 或锁频后 p50**，不要报未锁频的单点 p50。
5. **参考文件必须配对**：用 s90 的 ORT 参考评 s512 输出会得 13/16 FAIL，那是参考错配。

## 5. 验收纪律

- **判据是逐条 live 类排序**，不是 `rel_l2`。本项目中 `rel_l2` 骗过两次：
  RKNN w4a16 的 `rel_l2_full=7.1e-05` 看着比 fp16 还好而排序只有 6/16；
  探针报的 `logits rel_l2` 被 12 个 `-10000` 掩码哨兵主导（s512 报 1.7e-05，真实 live-only 是 4.20）。
- **层表也不能单独作判据**：融合版本层表全对（24 个 `exSDPAttention` 全在 NPU、fallback 0）而精度全崩。
- **单层简化通过 ≠ 可推广**：单层切片上修好掩码即恢复 16/16，完整模型上掩码只是并列问题之一。
- **改了想改的变量、病征却一字不动 → 病因在该变量之外**：qdq1→qdq2 摘掉残差流的 int8 后，
  `-4.640625` 在完全相同的 rows 上数值精确不变，据此立即放下残差假设。
  "改动生效了"（残差确实回 fp16、gemm 仍 int8）不等于"假设成立"。
- **定位数值退化不必先建 engine**：ORT 执行 Q/DQ 是真实算子、饱和算术与 TRT 相同，
  逐张量比对可在 114 s 的构建之前把发散点定死（本次即因此省掉一轮构建）。

## 6. 未验证 / 边界

- **离群通道抑制类量化口径未试** —— 显式 Q/DQ 已证明 int8 能落核（§3.4.1），失败在 per-tensor
  激活 scale。per-channel 激活 / SmoothQuant 一类换口径的方向未验证。
- **Jetson s512 的 17.5 ms 大头未定位** —— attention 二次项只占 22%，长序列（2048，二次项占 66%）
  才是它的主战场。
- **RK3588 上 seq > 512 未测**。
- **`/dev/shm` 会被静默清空**（radxa，累计实测多次）——传输+测量须在一条 detached 驱动里原子完成。
- RK3588 交付依赖固定版本工具链（torch 2.14 + transformers 5.17 的导出链路，
  环境在 wsl2-local `/mnt/f/laya-oldship/.venv`）。**换导出环境必须重跑 16 条排序验收。**
